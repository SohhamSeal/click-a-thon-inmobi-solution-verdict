Chapter 6: Evidence and Tracing

How claims are tracked, what ClickStack and HyperDX do, and how traces reach the console.

Simple first

What is "evidence" in Verdict?

Evidence is not a PDF attachment. It is structured, queryable proof stored in ClickHouse:

  • The accused segment and its test statistics
  • Every alternative candidate and why it was cleared
  • Step by step investigation log (what / why / result / SQL)
  • Confidence arithmetic you can dispute line by line
  • Coverage gaps (what we could not test)
Design principle: A verdict that only names a culprit is unfalsifiable. A verdict that also publishes exonerations can be checked: if the accused is wrong, the reason the right segment was cleared should be in the table.

Three consumers, one record

Each investigation step is captured once with three fields: what, why, result.

That single record feeds:

  1. HyperDX (via OpenTelemetry spans) for distributed trace waterfall
  2. case_steps table for durable audit inside ClickHouse
  3. Web console trace tree and waterfall UI
ClickStack and HyperDX

What is ClickStack?

ClickStack is the OpenTelemetry based observability stack used in this project. It exports traces, logs, and metrics via OTLP (OpenTelemetry Protocol).

In config (config/verdict.yaml):

tracing:
  enabled: true
  endpoint: http://localhost:4318   # OTLP HTTP
  service_name: verdict
  api_key: ${HYPERDX_API_KEY:-}     # HyperDX ingestion key

What is HyperDX?

HyperDX is the UI for viewing traces. With ClickHouse Cloud, traces are written to ClickHouse and HyperDX reads them from there. No extra container needed by default.

Each case stores a trace_id. The console links to HyperDX with the time range preset, because opening Live Tail on the wrong hour looks like a "lost" trace.

Span structure

Root span: investigate. Children include:

Span nameKindPurpose
auditstatisticsIs segment baseline trustworthy?
detectdetectorLattice sweep summary
detect:fill_rate:regiondetectorPer metric per combo detail
correctstatisticsBenjamini Hochberg
localize:fill_ratelocalizerCounterfactual tests
confidencescoringFive component score
narratellmProse generation + verification

case_steps row

Stored fields include:

  • what, why, result (human readable)
  • sql (queries run, so you can replay)
  • duration_ms, offset_ms (for waterfall positioning)
  • parent_id (tree structure)

offset_ms is measured from run start, not summed sibling durations. Real gaps between stages show as gaps in the waterfall.

Evidence ledger

case_candidates table

For each case, every candidate segment evaluated:

ColumnMeaning
statusaccused, cleared, partial, etc.
sufficiencypass / fail / unknown
minimalitypass / fail / unknown
maximalitypass / fail / unknown
holdoutpass / fail / unknown
reasonPlain English why cleared

coverage_gaps table

Cells not tested, with:

  • required denominator for detection
  • actual denominator available
  • resolvable_effect smallest drop detectable
  • reason e.g. below_detection_floor, non_positive_value

Self hosted ClickStack option

docker compose --profile selfhosted up -d
# Repoint console: NEXT_PUBLIC_HYPERDX_URL=http://localhost:8080

Console does not require HyperDX

The investigation view reads case_steps from ClickHouse. HyperDX is for comparing one run against everything else in the observability stack, not a hard dependency for reading a case.
