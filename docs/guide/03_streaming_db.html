Chapter 3: Streaming and the Database

How events flow into ClickHouse and become queryable rollups.

Simple first

The story of streaming (in this project)

"Streaming" here does not mean Kafka or live user traffic in production. It means: when new rows land in ClickHouse, rollups update automatically through materialized views, without a separate batch job.

  1. You run verdict load (or ingest from the console). Parquet rows insert into ad_events.
  2. A materialized view fires on each insert block. It fans each event into 46 lattice cells via one ARRAY JOIN.
  3. Counters (requests, fills, impressions, clicks, revenue) sum into rollup_5m.
  4. Another view aggregates 5m → 1h. Daily chains off hourly (not off 5m, because 5m is shallow).
  5. Within ~seconds, detectors can query rollups. No separate "build aggregates" step.
Think of it like: a spreadsheet that auto updates pivot tables whenever you paste new rows. The pivot tables are the rollups. The paste is the insert.
Going deeper

Why one ARRAY JOIN, not 46 views

Each combo could have its own materialized view. With 46 views, the streaming path and the backfill path have 46 chances to define a bucket boundary slightly differently. Any disagreement shows up as a fake step change in the data that looks like a real incident.

One shared SQL definition is used for both the live view and historical backfill, so they cannot drift.

Dictionaries

At rollup time, ClickHouse resolves app_id → category via a dictionary (dictGet), not a join. This keeps the fact table narrow and lookups fast.

Critical ops detail: on multi node ClickHouse Cloud, dictionary reload is node local. A stale dictionary can make row counts match but every segment name the wrong population. The loader now reloads ON CLUSTER and verifies each node.

Load verification (quiet failure modes)

The loader refuses to succeed if:

  • A CSV is a Git LFS pointer stub (looks valid, has almost no data)
  • Rollup totals disagree with raw event totals at any grain
  • Any one way combo does not sum to the grand total
  • Glossary metrics computed from raw vs rollup disagree

Performance: why batch reads matter

A 24 hour investigation issues ~20 ClickHouse queries totaling ~107ms server time. Wall clock is ~2.9s because of network round trips (~170ms each from a laptop to ap south 1).

Default read_mode: batch fetches the entire lattice (window + 4 baseline weeks) in one query. Alternative per_combo issues thousands of queries: same answers, 42.9s vs 1.9s.

Retention

Configured TTLs (raw 7d, 5m 30d, 1h 180d, 1d 730d) exist for production intent. retention.enforce defaults to false so historical hackathon data is not deleted on merge.
