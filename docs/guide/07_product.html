Starting the stack

cd click-a-thon-inmobi-solution-verdict
cp .env.example .env    # CLICKHOUSE_HOST, CLICKHOUSE_PASSWORD, etc.
./stack.sh up

docker compose exec verdict verdict schema apply
docker compose exec verdict verdict load
docker compose exec verdict verdict investigate --start 2026-07-05 --hours 24

Optional AI recommendations (off by default even when enabled):

./stack.sh up --with-ai   # needs CURSOR_API_KEY

The console: four tabs per case

1. Board (home)

Lists cases from the latest run, ranked by priority (impact × confidence). Header shows: open cases, revenue at risk, mean confidence, cells untested. The "untested" count is intentional honesty about coverage.

2. Trace

Two views of the same investigation steps:

  • Tree — hierarchical steps with what/why/result
  • Waterfall — timing bars using real offset_ms gaps

Example insight from a trace: audit runs before detect. On the unseen release, audit rejected segment baselines and forced sibling comparison.

HyperDX link in case header opens the same trace in the observability UI.

3. Evidence

  • Confidence breakdown: each component, weight, score, explanation
  • Full candidate table: accused + every cleared segment with rejection reason
  • Rate/mix decomposition when applicable

4. Narrative

Human readable summary. Numbers come from the computed bundle, not invented by the model. Badge shows whether LLM prose was verified or fell back to template.

5. Actions (optional)

Cursor CLI agent drafts remediation steps, then a second pass reviews them against evidence. Two gates: stack must be started with --with-ai, and user toggle must be on. Always labeled advisory. Pipeline verdicts do not depend on this.

Verdict.AI and MCP

Verdict.AI (chat)

Chat bubble backed by LibreChat with one tool: SQL against the same ClickHouse tables the detectors read. The agent is told the schema up front:

  • Rollups store counters, never pre computed rates
  • combo / key_a / key_b keying
  • Pipeline output tables and coverage ledger exist
  • A segment missing from cases was not necessarily innocent

It must show SQL so answers can be verified.

MCP for Cursor / other clients

{ "mcpServers": { "verdict-clickhouse": { "url": "http://localhost:8001/sse" } } }

Official ClickHouse MCP server with schema aware prompts.

Ingest from the console

The IngestPanel component can trigger loading new data without CLI. Same verification rules apply: rollups must reconcile with raw.

Investigate flags

  • --no-llm — template narrative only
  • --no-persist — dry run, no DB writes (~1.9s for 24h)
  • --grain 5m|1h|1d
  • --metric fill_rate (repeatable)

End to end demo story

  1. Load 9M event build corpus (+ optional unseen 1.5M bundle)
  2. Run investigate on a quiet day → few or no cases (clean window test)
  3. Run on July 8 to 9 → fill rate collapse visible in board
  4. Open case → trace shows audit → detect → localize path
  5. Evidence tab → see tier_3 accused for fill rate, iOS 17.5 in other metrics
  6. Ask Verdict.AI: "show me fill rate by os_version for July 8" → runs SQL, shows 0.48 for iOS 17.5
  7. Follow HyperDX link → see full span waterfall for the run
