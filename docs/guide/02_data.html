Chapter 2: The Data

What we ingest, how tables link, and how metrics are built from counters.

Simple first

What files exist

The hackathon dataset has one big fact file and three small dimension files:

FileWhat it isSize (approx)
ad_events.parquetEvery ad request event with timestamps and flags9M events (build corpus), 1.5M (unseen bundle)
apps.csvApp metadata: category, publisher tier2,000 apps
advertisers.csvAdvertiser metadata: vertical, campaign type500 advertisers
geo_device.csvDevice/geo profile: region, country, model, OS5,000 profiles

One ad event, in plain English

Each row in ad_events is one ad request at a moment in time:

  • Which app made the request (app_id)
  • Which device/geo profile (geo_device_id)
  • Which advertiser if filled (advertiser_id, empty if not filled)
  • Ad format (banner, video, etc.)
  • Flags: was it filled? impression shown? clicked?
  • Revenue earned (if any)
Key idea: IDs in the event file point to rows in dimension tables. app_id = 42 might mean category = Games, publisher_tier = tier_2. We never store those strings on every event. We look them up at query or rollup time.
Going deeper

The ten metrics

Important design rule: the database stores only additive counters. Metrics like fill rate are computed at read time as sum(fills) / sum(requests), never stored as pre averaged rates.

Why? If you average hourly fill rates to get a daily rate, you get the wrong answer unless every hour had identical traffic volume. Summing counters first is always correct.

The funnel and legal slices

Not every dimension exists at every stage of the ad funnel:

  1. Request — ad was requested (all events)
  2. Fill — ad was served (advertiser_id now known)
  3. Impression — ad was actually shown

advertiser_id is empty on unfilled requests. So dimensions like vertical and campaign_type only exist on filled events.

If you slice fill_rate by campaign_type, the denominator silently becomes "filled requests only" and every value looks like 1.0. That is an artifact, not a finding. Verdict derives a validity matrix from funnel stages so illegal slices are refused.

Dimensions in the lattice vs out

In lattice (scanned)Out of lattice (too high cardinality)
ad_format, category, publisher_tier, region, country, device_model, os_version, vertical, campaign_type app_id, advertiser_id, geo_device_id

The lattice has 46 combinations: grand total (__all__), 9 one way slices, and 36 two way pairs. Three way interactions are explicitly out of scope.

Revenue identity

Revenue can be walked multiplicatively:

Revenue ≈ Requests × Fill rate × Render rate × eCPM / 1000

When revenue moves, Verdict can attribute which factor moved first in log space, before blaming a specific segment. This stops a price problem from being reported as a volume problem.

Hierarchies

Some dimensions nest inside others:

  • region contains country
  • os_family contains os_version

The localizer respects these so it does not report both "EU" and "Germany" as separate root causes for the same incident.

The unseen bundle trap

In the final release, dimension tables were regenerated: same IDs, new attribute values. Only 147 of 2,000 app rows stayed identical. Rollups denormalize attributes at insert time, so old rollup rows encode old meanings.

Comparing July traffic to a June baseline for region = APAC can show −37% when the true growth trend is +5%. Verdict's baseline audit catches some of this and falls back to sibling comparison.
